# 프롬프트 변경을 측정으로 확인하기

## 무엇인가

LLM 출력 품질을 프롬프트로 손볼 때, **고쳤다고 믿는 것과 실제로 고쳐진 것을 가르는 방법**이다.
핵심 원칙: **프롬프트로 한 자리를 막으면 같은 동기가 옆에서 새 형태로 나온다.**
그래서 지켜져야 하는 것은 프롬프트가 아니라 코드가 쥔다.

이 스킬은 shotform 대본 파이프라인을 열 라운드 넘게 튜닝하며 실제로 겪은 실패에서 나왔다.
검증 방식은 서브에이전트 압력 테스트가 아니라 **실제 파이프라인 라이브 측정**이다
(규율 강제형 스킬이 아니라 방법 참조형이라 그렇게 뒀다).

## 언제 쓰나

- 프롬프트에 규칙을 넣었는데 출력이 안 바뀔 때
- 한 가지를 고치면 다른 것이 나빠질 때
- "좋아진 것 같다"를 근거 없이 말하려 할 때
- 임계값·가드를 감으로 정하려 할 때

## 회피 연쇄 — 가장 중요한 관찰

규칙을 조일 때마다 모델은 **같은 동기(안전하게 채우기)를 다른 형태로** 실현했다.

```
광고 카피 금지  →  요지를 조사만 바꿔 옮김(전사)
전사 금지       →  화면 설명을 읊음
그것도 금지     →  같은 말 되풀이
분량 요구       →  자료에 없는 사실을 지어냄
길이 조임       →  요약체로 후퇴
```

각 라운드는 앞 라운드 문제를 **실제로** 고쳤다. 그런데 옆에서 새 형태가 나왔다.
**한 자리를 막을 때 옆자리를 함께 보라.** 그리고 반복되면 프롬프트를 그만 조이고 코드로 판정하라.

## 프롬프트가 할 일과 코드가 할 일

| | 맡길 것 |
|---|---|
| 프롬프트 | 창작, 판단, 무엇을 고를지 |
| **코드** | **지켜져야 하는 것** — 길이, 원문 보존, 중복, 개수 |

가장 큰 소득은 **구조로 불가능하게 만들기**였다.
컷 분할에서 LLM에게 텍스트를 만들게 하지 않고 **경계 번호만** 받고 코드가 잘랐다.
그러자 "원문이 바뀌었나"를 확률로 재던 판정이 **구조적 보장**이 됐다.

> 모델에게 무엇을 시킬지 정할 때 묻는다: 이건 창작인가, 지켜져야 하는 규약인가.

## 임계는 실측에서 뽑는다

감으로 정한 임계는 두 번 다 틀렸다. 방법은 이렇다.

1. 실제 출력을 20~30개 모은다(정상 사례와 실패 사례 섞어서)
2. 각각을 지표로 재서 **두 무리의 분포를 본다**
3. 그 사이를 가른다. 정상 쪽에 여유를 준다

```
전사 0.55~0.75  /  정상 0.16~0.44   →  임계 0.5
```

**지표의 분모를 의심하라.** 두 번 틀렸다.
- 원본 길이로 나누니 → 원본이 긴 경우(화면 설명)를 놓쳤다
- 짧은 쪽으로 나누니 → 제대로 쓴 문장을 잡았다
- 정답은 **"이 결과물이 제 몫을 얼마나 하는가"** = 결과물 길이로 나누기

## 예시 오염 — 두 번 겪었다

프롬프트의 ✓/✗ 예시를 **테스트에 쓸 자료와 같은 소재로 쓰면 모델이 통째로 베낀다.**

```
예시: "물레는 안 가르칩니다…"   +  자료: 도자기 공방   →  예시를 그대로 출력
예시: "직접 삶습니다 → 단맛이…"  +  자료: 세탁소       →  "직접 삶아 세탁"(환각)
```

두 번째는 업종을 바꾼 뒤에도 터졌다 — **동사까지 겹치면 샌다**(삶다는 조리·세탁 양쪽).
개선인지 복사인지 구분할 수 없어 한 라운드를 통째로 버렸다.

> 예시는 쓰게 될 자료와 **소재도 동사도** 겹치지 않게 고른다.

## 부분 개선을 버리지 마라

되돌리기(재생성) 결과를 받을지 판정할 때 **"결함 개수가 줄었는가"로 재면 절반 고친 것을 버린다.**

```
265자 → 220자로 줄여 옴. 여전히 초과 → 결함 개수 동일 → 기각 → 원본 유지
```

점수를 매겨라: `결함 수 × 큰 가중치 + 목표와의 거리`. 개수를 먼저 보되, 같으면 거리로 가른다.
같은 실수를 두 번 했다(문단 단위 병합에서 한 번, 원고 통짜에서 또 한 번).

## 측정 없이 말하지 마라

라운드마다 이걸 지켰다.

- **표본 1회로 결론 내지 않는다** — 같은 입력으로 2~3회. LLM 변동이 라운드 간 차이보다 클 때가 있다
- **기계 지표를 그대로 믿지 않는다** — A/B에서 지표는 A 우세였는데 실제 출력은 B가 나았다.
  지표가 A가 받은 문장과의 표면 일치를 쟀기 때문이다(**편향된 지표**)
- **파이프라인 안에 로그를 남긴다** — 라운드별 글자 수·결함·점수·채택 여부.
  "3회를 다 쓴 건지 일찍 멈춘 건지"는 추측으로 갈리지 않는다. 로그를 붙이자 원인이 예상과 달랐다
  (되돌리기가 아니라 **교정 패스가 분량을 불리고** 있었다)

## 측정 도구

이 저장소의 `scripts/measure/`:

| 스크립트 | 무엇 |
|---|---|
| `run-pipeline.mjs` | 자료 → 시나리오 → 컷 → 화면까지 태우고 지표 출력 |
| `scenario.mjs` | 시나리오 지문의 규칙 위반율(1차/최종)·장면 분포·내레이션 비율 |

서버가 `localhost:3000`에 떠 있어야 한다. 이미지 비용을 안 쓰려면 `SHOTFORM_FAKE_IMAGES=1`.

## 흔한 실수

| 실수 | 결과 |
|---|---|
| 프롬프트에 두 번 적고 지켜지리라 믿기 | 두 번 다 어겼다(소개문 오프닝) → 코드 판정으로 |
| 한 프롬프트에 성격이 반대인 두 일 시키기 | 모델이 쉬운 쪽으로 도망간다(원문 보존 vs 창작은 나눠라) |
| 규칙 후보를 목록으로 나열하기 | 모델이 자료를 대조하는 대신 **목록을 채운다** |
| 상한만 주고 하한 안 주기 | 짧은 쪽으로 도망간다(반대도 성립) |
| 하한만 주고 재료 검사 안 하기 | 없는 사실을 지어내 채운다. "짧은가"가 아니라 **"채울 재료가 남았는가"**를 물어라 |
| `npm run build`를 dev 서버 켜둔 채 실행 | `.next`가 덮여 dev 서버가 죽는다 |
