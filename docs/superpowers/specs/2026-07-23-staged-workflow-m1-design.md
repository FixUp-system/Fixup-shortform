# 단계별 생성 워크플로우 M1 (이미지 게이트까지) — 설계

2026-07-23. 근거: 빠른 생성 실험 결론 — 짧은 입력으로는 원하는 품질 불가(정보량 부족). 해법 = 수집 심화(①) + 싼 단계에서 의도 고정(④게이트). 전체 설계는 브레인스토밍 D1~D12·목업 v4 참조.

## 범위

**M1**: ①자료·설정 → ②대본 생성 [게이트 1] → ③컷 분할 + 컷별 이미지 생성 + VLM 선별 [게이트 2]
- 포함: 텍스트 자료 입력, 사진 업로드(컷 소스 + AI 컷 레퍼런스 D10), 대본 수정·재생성, 컷별 이미지 재생성(3회 D3), 비용 기록 연동
- 제외(후속 M2): 영상화(i2v)·클립 게이트, 병합(TTS·BGM·자막), 파일(PDF) 자료 업로드, 아바타(D9), 모델 라우팅 고도화(D7 — M1은 이미지 모델 1종 고정), 템플릿, 인증·크레딧

## 사용자 흐름

```
사이드바 "영상 만들기 (단계별)" (활성화됨)
 1 자료·설정: 텍스트 자료(2,000자) + 사진 업로드(≤10장) + 목적/길이(15·30·45·60s)/비율 → [대본 만들기 · 무료]
 2 대본 확인 [게이트1]: 전체 대본(문단+역할 태그) + 자료 반영 체크리스트
    → 부분 수정(문단 클릭 편집) · 전체 다시 쓰기 · 지시 입력("더 짧게" 등)
    → [대본 승인 — 컷 나누고 이미지 만들기]
 3 이미지 확인 [게이트2]: 진행 표시(컷 분할→이미지 생성→VLM 선별) 후 컷 리스트
    - 컷 = 이미지(or 내 사진) + 문장 + 배지(AI/내 사진·레퍼런스·초)
    - AI 컷: [다시 생성](컷당 3회) · 내 사진 컷: [사진 바꾸기]
    - 컷 문장 수정 → 소스 재판정 제안(D12)은 M1에서 문장 수정만 지원, 재판정 제안은 후속
    → 이 화면이 M1의 끝 (다음 단계 버튼은 "영상화 — 준비 중" 비활성)
```

## 아키텍처

### 저장 (로컬 파일, 배포 시 Supabase 이관)
`data/projects/<id>.json` — 프로젝트 단위 단일 문서:
```
{ id, created_ts, status: "draft"|"script"|"cuts",
  settings: { purpose, duration_s, aspect_ratio },
  material: { text, photos: [{id, filename, path}] },   // 사진은 data/uploads/에 저장
  script: { paragraphs: [{tag, text}], coverage: [..], version },
  cuts: [ { idx, sentence, seconds, source: "ai"|"photo",
            photo_id?, ref_photo_id?,                    // D10: AI 컷의 레퍼런스
            image?: {url, path}, vlm: {passed, note},
            regen_count } ] }
```

### API (Next.js route handlers)
| 라우트 | 역할 |
|---|---|
| `POST /api/projects` | 프로젝트 생성 (자료·설정 저장) |
| `GET/PATCH /api/projects/[id]` | 조회 / 자료·설정·컷 문장 수정 |
| `POST /api/projects/[id]/script` | gpt-4o 대본 생성(또는 지시 반영 재생성) → script 저장 |
| `POST /api/projects/[id]/cuts` | 대본 승인 → gpt-4o 컷 분할(문장·초·소스·레퍼런스 판정) → 컷별 이미지 생성 시작 |
| `GET /api/projects/[id]/cuts/status` | 컷별 진행 상태 폴링 (프론트 진행 화면용) |
| `POST /api/projects/[id]/cuts/[idx]/regen` | 해당 컷만 이미지 재생성 (3회 제한) |

컷 이미지 생성은 요청당 컷 병렬(Promise.all) + 컷당: 후보 2장 생성 → VLM 검수 → 선택. 전원 탈락 시 프롬프트 보정 1회 자동 재생성(D4, 크레딧 개념 없음·비용기록만).

### 모델
- **대본·컷 분할**: gpt-4o (기존 키) — 대본은 자료 전체를 입력으로, 컷 분할은 대본+사진 목록을 입력으로 "각 컷의 문장/초/소스(사진이 그 컷을 보여줄 수 있으면 photo)/AI 컷 레퍼런스 사진" JSON 산출
- **이미지 생성**: fal `fal-ai/nano-banana` (레퍼런스 이미지 입력 지원 → D10 구현 가능, ~$0.04/장). env `FAL_IMAGE_ENDPOINT`로 교체 가능
- **VLM 검수**: gpt-4o vision — 후보 이미지 2장 + 컷 문장 + (레퍼런스 사진) → {selected, passed, note} JSON. 검수 항목: 문장 의도 일치·신체 오류·레퍼런스 피사체 일치
- 비용 기록: 이미지 생성 건도 `lib/costs.js`에 기록 (단가표에 이미지 항목 추가)

### UI
- 사이드바 "영상 만들기 (단계별)" 활성화 + 세로 스테퍼(1~3, 목업 v4 스타일) — 4·5단계는 "준비 중" 표시
- `/create/[id]` 단일 페이지에서 단계 화면 전환, 진행 상태는 서버 폴링(새로고침해도 이어짐)
- 디자인: 기존 globals.css 토큰·컴포넌트 재사용

## 오류 처리
- 이미지 후보 전원 탈락 → 자동 보정 재생성 1회 → 그래도 실패 시 해당 컷 "품질 확인 필요" 마킹, 나머지 컷은 정상 진행(실패 격리). 사용자는 [다시 생성]으로 해결
- fal/OpenAI 오류 → 컷 단위 실패 마킹 + 재시도 버튼. 프로젝트 전체가 죽지 않음
- 업로드 사진: 형식(jpg/png/webp)·크기(≤10MB) 검사, 실패 시 그 자리에서 반려
- 서버 재시작/브라우저 이탈 → 파일에 저장된 상태에서 이어짐 (단, 진행 중이던 생성 요청은 유실 가능 — 상태가 "생성 중"으로 5분 이상이면 재시도 안내)

## 검증
- `npm run build` + 대본·컷분할·VLM 응답의 JSON 스키마 방어(파싱 실패 시 1회 재요청 — 기존 chat 패턴)
- e2e 수동: 자료 입력→대본→이미지 게이트까지 실키 1회 (사용자와 함께, 카페 시나리오)
- 컷 분할 로직 검증 포인트: 사진이 있는 시나리오에서 photo/ai 소스 판정과 레퍼런스 지정이 상식적인지
