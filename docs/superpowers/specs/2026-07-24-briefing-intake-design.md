# 자료 수집과 브리핑 확정

날짜: 2026-07-24 / 브랜치: `feature/deferred-settings` 후속
관련: `2026-07-24-pipeline-roadmap.md`(기준), `2026-07-24-pipeline-spec-source.md`(원문)

## 배경

07-23 실험의 결론은 "짧은 입력으로는 품질이 안 나온다 — 정보량이 본질"이었다. 그런데 지금 1단계는 자유 텍스트 한 칸이 전부다. 사장님이 두 줄만 쓰면 대본도 두 줄어치가 되고, 그걸 막을 장치가 없다.

자유 입력을 폼으로 바꾸는 게 답처럼 보이지만, **폼은 입력의 존재를 강제할 뿐 품질을 강제하지 못한다.** 칸이 열 개여도 한 글자씩 쓰면 그만이다. 그래서 폼을 앞세우지 않는다.

## 설계 원칙

1. **필수는 최소, 보강은 적응형** — 처음부터 다 받지 않는다. 부족한 것만 되묻는다.
2. **작성보다 수정** — 백지를 채우게 하지 않고, 기계가 정리한 초안을 고치게 한다.
3. **질문은 선택지형** — 답변 속도와 품질 모두 유리하다.
4. **되묻는 것은 정보가 있어야만 채워지는 것으로 한정** — 훅이 약한 건 프롬프트 문제지 사장님 잘못이 아니다. 그건 대본 단계가 자동으로 처리한다.

## 사장님이 겪는 흐름

```
① 자료
┌ 레퍼런스 자료 ────────────────┐   (지금과 동일)
│ 제품 설명·홍보 문구·이야기…    │   사진 [+][+]
└──────────────────────────────┘
            [ 정리하기 ]
                 ↓
╭─ 이렇게 이해했어요 ─────────────╮
│ 주제      생딸기라떼 신메뉴     │  ← 칸은 결과물로 등장. 클릭해 고침
│ 핵심내용  • 매일 아침 직접 갈아 │
│           • 시럽 안 씀         │
│ 대상      (비어 있음)          │
│ 보고 나면 매장 방문            │
╰────────────────────────────────╯
╭─ 두 가지만 더 여쭤요 ───────────╮
│ 누가 보게 될까요?              │
│ [20~30대 여성][동네 주민][직접] │
│ 가격대는요?  [      ] 건너뛰기 │
╰────────────────────────────────╯
        [ 이대로 대본 만들기 ]   ← 개입 지점 ①
```

핵심은 **사장님이 백지를 채우지 않는다**는 것이다. 자유롭게 던지면 기계가 정리하고, 사장님은 틀린 것만 고친다. 빈 칸이 눈에 보이므로 무엇을 안 알려줬는지가 저절로 드러나고, 그중 중요한 것만 질문이 된다.

**단계는 늘지 않는다** — 폼·질문·브리핑이 모두 ①자료 안에서 일어나므로 사이드바는 6단계 그대로다. 다만 라우트는 하나 는다. [정리하기]를 누르는 순간 프로젝트가 생기므로, 그 뒤의 화면은 프로젝트에 속해야 새로고침해도 살아남는다.

| ①자료의 주소 | 언제 |
|---|---|
| `/create` | 프로젝트 생기기 전 — 자료 입력 |
| `/create/[id]/briefing` | 프로젝트 생긴 뒤 — 브리핑 카드·질문·확정 |

`stepHref(material, id)`가 프로젝트 유무로 갈라진다(현재는 항상 `/create`). 자료를 통째로 다시 쓰고 싶으면 브리핑 화면에서 원문을 그대로 고칠 수 있게 두고, `/create`로 되돌리지 않는다 — 되돌리면 새 프로젝트가 하나 더 생긴다.

## 브리핑 스키마

`project.briefing`에 저장한다.

```js
{
  topic: "생딸기라떼 신메뉴",        // 무엇에 대한 영상인가
  key_points: ["매일 아침 직접 갈아", "시럽 안 씀"],  // 대본의 살
  audience: "",                      // 누가 보나 (비어 있을 수 있음)
  cta: "매장 방문",                  // 보고 나서 뭘 하길 바라나
  asked: [                           // 되물은 이력 — 라운드 상한 판정과 로깅에 쓴다
    { question: "누가 보게 될까요?", answer: "20~30대 여성" },
    { question: "가격대는요?", answer: null }   // null = 건너뜀
  ],
  confirmed: false,
  version: 1
}
```

`key_points`가 대본 품질의 실질이다. 대본의 `coverage`는 이 배열을 반영했는지로 검증된다.

## 단계 전이

`project.status`에 `briefing`을 추가한다.

| 상태 | 뜻 | 다음 |
|---|---|---|
| `draft` | 자료만 있음 | [정리하기] → 추출 |
| `briefing` | 브리핑 초안·질문 있음, 미확정 | [이대로 대본 만들기] → 확정 |
| `script` | 대본 생성됨 | 기존과 같음 |
| `cuts` | 컷·이미지 | 기존과 같음 |

`lib/steps.js`의 `currentStepKey`는 `draft`·`briefing`을 ①자료로, `script`를 ②대본으로 본다. 지금은 `draft`가 ②대본(자동 생성 중)이었으므로 이 판정이 바뀐다.

## API

| 엔드포인트 | 동작 |
|---|---|
| `POST /api/projects` | 지금과 같음(자료만 받아 `draft` 생성). [정리하기]가 이걸 먼저 부르고 곧바로 아래를 부른다 |
| `POST /api/projects/[id]/briefing` | 자료(텍스트+사진 파일명) → LLM 추출 → `briefing` 초안 + 부족분 질문 저장, `status: "briefing"`. 재호출하면 다시 추출(추출 실패 후 재시도용) |
| `PATCH /api/projects/[id]` | `briefing` 부분 수정(칸 편집·질문 답변)을 기존 PATCH에 얹는다 |
| `POST /api/projects/[id]/script` | **`briefing.confirmed`를 요구**한다. 확정 없이 부르면 400 |

확정은 별도 엔드포인트를 두지 않고 `PATCH { briefing: { confirmed: true } }` → `POST /script` 순서로 처리한다. 확정 자체가 저장할 상태 변화라 PATCH로 충분하다.

## 부족분 판정

추출과 같은 LLM 호출에서 질문까지 함께 받는다(별도 호출 없음).

- **최대 3개**, 각 질문은 보기 2~4개 + 직접 입력 + 건너뛰기
- **질문 라운드는 1회.** `briefing.asked`가 비어 있지 않으면 다시 묻지 않는다
- 질문 대상은 **정보가 있어야만 채워지는 것**으로 한정한다(가격·위치·기간·대상 등). "더 매력적인 표현" 같은 건 묻지 않는다
- 자료가 이미 충분하면 질문 0개로 돌아올 수 있다 — 그 경우 질문 카드를 그리지 않는다

## 추출이 실패하면

LLM 추출은 실패할 수 있다(빈 JSON·스키마 불일치·네트워크). 이때 **백지 폼으로 떨어진다** — 빈 브리핑 카드를 편집 가능한 상태로 띄우고 사장님이 직접 칸을 채우게 한다. 재시도 버튼도 함께 둔다. 자동 재시도는 1회까지.

이 폴백이 있어야 "정리하기를 눌렀는데 아무 일도 안 일어남"이 생기지 않는다.

## 대본 생성에 미치는 영향

`buildScriptMessages`는 브리핑과 원문 자료를 **둘 다** 넣는다. 브리핑은 구조를, 원문은 브리핑이 놓친 디테일을 준다. 원문을 버리면 정보가 준다.

## 하지 않는 것

- **카테고리 선택** — 폼은 범용 단일 세트다
- **URL 추출**(`SourceAdapter`) — 자료는 사장님이 직접 준 것만. 네이버 봇월 리스크도 함께 없다
- **고성과 숏폼 레퍼런스 수집·전사·분류**
- **`template_meta`(hook_type·structure_type) 라벨링** — 성과 데이터를 붙일 경로가 없어 지금은 아무것도 알려주지 않는다
- **문서 파일(PDF·docx) 파싱** — 후속. 이번엔 텍스트 + 사진
- **대본 생성·판정 루프(판정 2)** — 밀접하지만 별도 스펙으로 뗀다. 이 스펙은 자료 수집과 브리핑 확정까지다

내부 행동 로깅(대본 수정 diff·컷 재생성 횟수·질문 응답)은 남긴다. 연동 없이 당장 프롬프트를 고치는 데 쓰는 신호다. 단, 이 스펙에서는 `briefing.asked`(어떤 질문에 답이 왔고 무엇을 건너뛰었나)까지만 저장한다.

## 테스트

- `buildBriefingMessages`: 자료 텍스트·사진 파일명이 프롬프트에 들어간다
- `validateBriefing`: 필수 필드 누락·타입 불일치를 거른다. 질문 3개 상한을 넘기면 잘라낸다
- 라운드 상한: `asked`가 있으면 추출이 질문을 다시 만들지 않는다
- `POST /script`가 `confirmed: false`면 400
- `currentStepKey`: `draft`·`briefing` → 자료, `script` → 대본
- `stepHref`: 프로젝트가 없으면 `/create`, 있으면 `/create/[id]/briefing`
- `buildScriptMessages`가 브리핑과 원문을 모두 담는다

기존 34개 그린 유지가 하한선이다.
