# 회원가입·비밀번호 로그인 (2026-08-06)

매직링크를 걷어내고 **이메일+비밀번호**로 바꾼다. 메일 왕복이 사라지고, 사람마다 계정을
갖는 축(소유자·actor·크레딧)은 그대로 남는다.

## 왜

매직링크는 메일 왕복이 필수라 실사용에서 계속 걸렸다 — 전송 한도가 "주소 오류"로 보이고
(08-03 실측), 링크를 주고받는 것만으로 토큰이 소모되며, 커스텀 SMTP 가 아직 없다.
비밀번호는 그 왕복을 통째로 없앤다.

## 확정된 결정

| 결정 | 내용 |
|---|---|
| 방식 | 이메일+비밀번호 **회원가입·로그인**. 사람마다 계정(공유 암호 아님) |
| 이메일 인증 | **안 받는다** — 가입 즉시 로그인된다. 가짜 주소는 승인제가 거른다 |
| 승인제 | **그대로 유지.** 가입은 누구나 되지만 승인 전에는 `/pending` 에서 아무것도 못 한다 |
| 화면 | `/login` 한 페이지에 탭 둘(로그인 / 회원가입). 새 화면을 만들지 않는다 |
| 비밀번호 분실 | 자가 재설정 화면을 **만들지 않는다**(메일 왕복이 되돌아온다). `/admin` 에 [비밀번호 재설정] 을 달아 운영자가 처리 |
| 매직링크 | `signInWithOtp`·`/auth/callback`·전송 한도 처리를 **걷어낸다** |
| 개발 우회 | `SHOTFORM_DEV_USER` 는 **남긴다**(콜백을 안 쓰므로 영향 없음) |

## 흐름

```
처음 온 사람  /login → [회원가입] → 이메일·비밀번호 → 즉시 로그인 → /pending
                     → 운영자 승인 → 앱 사용
돌아온 사람   /login → 이메일·비밀번호 → 앱
```

## 아키텍처

```
POST /api/auth/signup { email, password } → supabase.auth.signUp        → 세션 쿠키
POST /api/auth/login  { email, password } → signInWithPassword          → 세션 쿠키
```

- 두 라우트는 `lib/auth/supabase-server.js` 의 `authClient(cookieStore)`(anon 키 + 쿠키
  어댑터)를 쓴다. 이미 세션 쿠키를 쓸 줄 아는 물건이라 새로 만들 것이 없다
- 세션이 선 뒤는 **지금과 완전히 같다** — middleware 검증, `withUser`, `owner_id`, `actor`,
  크레딧, RLS 가 한 줄도 안 바뀐다
- 가입 시 `handle_new_user` 트리거가 `profiles` 행을 `status='pending'` 으로 만든다(이미 그렇다)
- 비밀번호는 우리가 저장하지 않는다 — 해시·시도 제한은 Supabase 몫이다
- 공개 경로(`PUBLIC_PATHS`)는 `/login` 과 `/api/auth/signup`·`/api/auth/login` **셋뿐**.
  `/auth/callback` 은 목록에서 빠진다

⚠️ **Supabase 대시보드에서 "Confirm email" 을 꺼야** 가입 즉시 로그인된다. 코드가 아니라
설정이므로 배포 절차 문서에 적는다. 켜져 있으면 가입은 되는데 로그인이 안 되어
"가입했는데 못 들어간다"로 보인다.

## 화면

`app/login/page.js` 를 탭 둘로 바꾼다(패널·버튼 클래스는 기존 그대로 — `tests/design-system.test.js`).

- **로그인 탭**: 이메일·비밀번호·[로그인]
- **회원가입 탭**: 이메일·비밀번호·[가입하기] + "승인 뒤에 쓸 수 있어요" 안내
- 실패 문구는 **한 가지로 통일**한다: *"이메일 또는 비밀번호가 맞지 않아요"* — 어느 이메일이
  가입돼 있는지 흘리지 않게. 가입 실패(이미 있는 주소·약한 비밀번호)는 그 자체가 사용자에게
  필요한 정보라 원인을 풀어 준다
- `useSearchParams`·`Suspense` 구조는 콜백이 사라지므로 함께 걷어낸다

## 운영자 비밀번호 재설정

`/admin` 사용자 행에 **[비밀번호 재설정]**. 운영자가 새 비밀번호를 입력하면
`POST /api/admin/users/[id]/password` 가 `admin.auth.admin.updateUserById(id, { password })`
로 바꾼다(승인·차단 라우트와 같은 service_role 클라이언트 패턴).

- 운영자 전용(`withUser({ adminOnly: true })`)
- 비밀번호는 **응답·로그에 싣지 않는다**
- 감사: 누가 언제 재설정했는지 `console.log` 로 남긴다(전용 장부는 만들지 않는다 — 지금
  단계에서 표를 하나 더 두는 값이 재설정 빈도보다 크다)

## 테스트로 못 박을 것

- 가입하면 세션이 서고 `profiles` 에 `pending` 행이 생긴다. **승인 전에는 보호된 라우트가 막힌다**
- 로그인 실패(틀린 비밀번호·없는 계정)가 **같은 문구·같은 상태코드**로 나간다
- 비밀번호가 응답 본문·로그에 안 실린다
- 공개 경로가 `/login`·`/api/auth/signup`·`/api/auth/login` 셋을 넘지 않는다
  (`lib/auth/paths.js` 를 소스로 판정)
- 매직링크 잔재(`signInWithOtp`·`auth/callback`)가 0건
- 비밀번호 재설정은 **운영자만** 가능하고(비운영자 403), 없는 사용자면 404

## 이번 스펙에 넣지 않는 것

- 자가 비밀번호 재설정·이메일 변경·소셜 로그인
- 비밀번호 규칙 강화(Supabase 기본 최소 길이를 따른다)
- 세션 유지 기간 조정(지금 기본값 그대로)
