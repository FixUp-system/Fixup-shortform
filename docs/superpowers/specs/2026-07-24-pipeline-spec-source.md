# AI 숏폼 영상 생성 SaaS — 파이프라인 설계 스펙 (원문)

> 2026-07-24 사용자 제공 원문. 화해 버전은 `2026-07-24-pipeline-roadmap.md` 참조.
> 이 파일은 수정하지 않는다 — 판단의 출처를 남겨두기 위한 사본이다.

---

## 1. 제품 개요

- **입력**: 영상 주제(또는 원고 초안), 타깃 플랫폼(틱톡/릴스/쇼츠), 영상 길이, 스타일 선호
- **출력**: 자막·내레이션·BGM이 포함된 완성 숏폼 영상 (9:16, 플랫폼별 인코딩 프리셋)
- **핵심 원칙**:
  1. 결정적으로 처리 가능한 것(타이밍 계산, 병합, 인코딩)은 전부 코드로 처리. LLM은 창작 영역에만 사용
  2. 비싼 단계(영상 생성) 이전에 사용자 확정 지점을 배치해 재작업 비용 최소화
  3. 모든 중간 산출물 저장 → 어느 단계에서든 부분 재실행 가능

---

## 2. 파이프라인 (확정 순서)

```
① 씬 분해 (구조화 JSON 생성)
② 대본 확정        ← 사용자 개입 지점 1
③ TTS 생성 → 씬별 타이밍 확정
④ 스타일/캐릭터 레퍼런스 생성  ← 사용자 개입 지점 2 (승인)
⑤ 씬별 이미지 생성 + 자동 QC
⑥ 이미지 → 영상화(클립 생성) + 자동 QC
⑦ 사용자 검수 및 씬 단위 재생성  ← 사용자 개입 지점 3
⑧ 자막 생성 + 병합/오디오 믹싱/인코딩 (전부 코드, ffmpeg)
```

**중요한 순서 결정**: 영상 클립 길이는 오디오(TTS)가 결정한다.
TTS를 먼저 생성해 씬별 실제 오디오 길이를 확정한 뒤, 그 길이에 맞춰 클립을 생성한다.
(반대 순서로 하면 영상 5초 + 내레이션 7초 같은 미스매치가 구조적으로 발생)

---

## 3. 단계별 상세 요구사항

### ① 씬 분해 — 구조화 JSON

- 자유 텍스트 대본이 아니라 처음부터 JSON 스키마로 생성 (이후 단계가 이 스키마를 파싱)
- 숏폼 구조 강제: 훅(0~3초) → 전개 → CTA

```json
{
  "video_id": "uuid",
  "target_platform": "tiktok | reels | shorts",
  "total_duration_sec": 30,
  "scenes": [
    {
      "id": 1,
      "role": "hook | body | cta",
      "duration_sec": 3,
      "narration": "내레이션 텍스트",
      "visual_description": "화면 묘사 (이미지 프롬프트의 원천)",
      "camera": "close-up | wide | ...",
      "mood": "urgent | calm | ..."
    }
  ]
}
```

### ③ TTS / 오디오

- TTS: 씬별 내레이션 → 오디오 파일 + **character-level 타임스탬프** 확보 (자막 생성에 사용)
- 씬별 `actual_audio_duration`을 씬 JSON에 기록 → 이후 클립 길이의 기준값
- BGM: 무드 기반 선택(라이브러리), 효과음은 v2 범위

### ④ 일관성 관리 — 레퍼런스 시스템

- 씬별 독립 이미지 생성 시 인물/스타일/색감 불일치가 최대 품질 문제
- 해결:
  - 캐릭터/스타일 **레퍼런스 시트를 먼저 1회 생성**, 사용자 승인 후 전 씬에 reference image로 주입
    (모델별: Midjourney cref, Flux/SDXL IP-Adapter, 각 모델의 character reference 기능)
  - 스타일 토큰(색 팔레트, 조명, 렌즈)을 전 씬 프롬프트 공통 suffix로 고정
  - 시드 고정만으로는 불충분 — 레퍼런스 주입이 필수

### ⑤⑥ 이미지 생성 / 영상화

- 씬 JSON → 모델별 프롬프트 변환은 **모델 어댑터 레이어**로 분리 (아래 4절)
- 각 산출물마다 **자동 QC 선행** (사용자에게 실패작 검수 노동을 시키지 않음):
  - VLM 기반 검사: 프롬프트 일치 여부, 손/얼굴 붕괴, 텍스트 깨짐, 레퍼런스와의 일관성
  - QC 실패 → 자동 재생성 (최대 재시도 횟수 제한, 비용 로깅)

### ⑦ 사용자 검수 / 재생성

- **재생성 단위를 씬 단위로 분리**. 사용자가 선택 가능한 액션:
  - 이미지만 재생성 (영상화 재실행 포함)
  - 영상화만 재시도 (이미지 유지)
  - 프롬프트/대본 수정 후 해당 씬 재생성
- 전체 재실행 없이 특정 씬만 교체 가능해야 함
- **재생성 비용 정책**: 영상 생성 API 호출 비용이 크므로 크레딧 차감 규칙 필요 (무제한 재생성 금지)

### ⑧ 병합/후처리 — 전부 코드(ffmpeg), LLM 미개입

- 자막: TTS 타임스탬프 → 자막 자동 생성, 번인 또는 스타일드 캡션
  - **세이프존 준수**: 틱톡/릴스 UI가 가리는 영역을 피해 배치
- 오디오: 씬 간 크로스페이드, BGM 덕킹(내레이션 아래로), 라우드니스 정규화 **-14 LUFS**
- 트랜지션: 컷/디졸브 (씬 JSON에 트랜지션 타입 필드 추가 가능)
- 인코딩: 플랫폼별 프리셋 (9:16 해상도, 코덱/비트레이트)

## 4. 아키텍처 요구사항

### 비동기 잡 큐 + 상태 머신 (필수)

- 전체 파이프라인이 분 단위 → 동기 처리 불가
- 잡 오케스트레이션: Temporal / BullMQ / Celery 중 스택에 맞게 선택
- 씬 단위 상태: `pending → generating → qc_failed → regenerating → done`
- **부분 실패 복구**: 씬 6개 중 5개 성공 시 성공분 캐싱, 실패분만 재시도
- 외부 API 장애/레이트리밋 대응: 지수 백오프 재시도, 폴백 모델 지정 가능 구조

### 모델 어댑터 레이어

- 이미지/영상 생성 모델은 교체 주기가 짧음 → 어댑터 패턴으로 분리
- 인터페이스 예시:
  ```
  ImageGenAdapter: (scene, style_ref) → image
  VideoGenAdapter: (image, scene, duration) → clip
  TTSAdapter: (narration, voice) → audio + timestamps
  ```
- 신모델 추가 시 어댑터만 구현하면 되는 구조

### 산출물 저장 / 재개

- 모든 중간 산출물 저장: 씬 JSON, 오디오, 타임스탬프, 레퍼런스 시트, 이미지, 클립
- 어느 단계에서든 재개(resume) 가능해야 함

### 비용 추적

- 잡당·씬당·API 호출당 비용 로깅 → 가격 정책/크레딧 시스템의 근거 데이터

## 5. 사용자 개입 지점 (3곳으로 고정)

| 지점 | 단계 | 사용자 액션 |
|---|---|---|
| ① | 대본 확정 | 씬별 내레이션/구성 수정 후 확정 |
| ② | 레퍼런스 승인 | 캐릭터/스타일 시트 승인 또는 재생성 요청 |
| ③ | 최종 검수 | 씬 단위 재생성, 최종 렌더 승인 |

- 설계 의도: 비싼 영상 생성 **이후에** 대본을 고치는 상황을 구조적으로 차단

---

## 6. 구현 우선순위 제안

1. **P0**: 씬 분해 JSON 스키마 + LLM 프롬프트, 잡 큐/상태 머신 골격, TTS→타이밍 확정 플로우
2. **P1**: 이미지/영상 모델 어댑터 2종 이상, 레퍼런스 주입, ffmpeg 병합 파이프라인
3. **P2**: 자동 QC(VLM), 씬 단위 재생성 UI/API, 자막 스타일링
4. **P3**: 크레딧/비용 정책, 폴백 모델, BGM 자동 선택

---

## 7. 열린 결정 사항 (구현 전 확정 필요)

- 기술 스택 (백엔드 언어/프레임워크, 잡 큐 선택)
- 사용할 이미지/영상/TTS 모델 1차 라인업
- 스토리지 (S3 등) 및 렌더링 워커 인프라
- 크레딧 차감 단위 및 재생성 정책 수치
