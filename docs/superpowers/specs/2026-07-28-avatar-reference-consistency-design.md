# 인물 일관성 — 아바타 레퍼런스 설계 (2026-07-28)

**문제:** 컷마다 이미지를 완전히 독립적으로 그려서 같은 사람이 매번 다르게 나온다.
2026-07-28 관통에서 실제로 확인했다 — 컷 1의 아이와 컷 2의 아이가 다른 사람이었고,
**클립을 5회($1.7어치) 다시 만들어도 고쳐지지 않았다**(이미지 단계의 결함이라서).

인물을 이어줄 장치가 둘 있었지만 그 편에서는 둘 다 무력했다:

- `subject` 앵커 = `briefing.topic` = "성수동 자전거 수리점 소개" — 가게 얘기지 인물이 아니다
- 업로드 사진 레퍼런스 — 사장님이 올리지 않았다(`ref_photo: 없음`)

**목표:** 사장님이 사진을 주지 않아도 인물이 컷을 가로질러 같은 사람으로 나온다.

관련 문서: `docs/models-and-costs.md` §4(눈으로 본 결함 넷), `2026-07-28-prototype-local.md`

## 흐름

```
원고 승인
   │
   ├─ ① 캐스팅      원고를 읽고 등장 인물을 뽑고, 인물마다 아바타를 고른다
   │                (LLM, 편당 ~$0.003. 아바타 목록을 프롬프트로 함께 받는다)
   │                cast = [{ id:"c1", who:"가게 주인",    avatar_id:"av-owner" },
   │                        { id:"c2", who:"초등학생 아이", avatar_id:"av-child" }]
   │
   ├─ ② 사진 판정   올린 사진마다 무엇이 담겼나 (VLM, 장당 $0.006)
   │                p1 → { person:false, what:"가게 내부" }
   │                p2 → { person:true,  who:"50대 남성" } → c1 에 붙는다
   │
   ├─ ③ 사진 우선 적용  **코드가 한다.** 사진이 붙은 인물은 아바타를 버린다
   │                c1 → 사진 p2 (av-owner 는 쓰지 않는다)
   │                c2 → av-child (붙은 사진이 없다)
   │
   ├─ ④ 컷 분할 · 화면 설계  컷마다 누가·무엇이 나오는지 고른다
   │                cut.ref_ids = ["c2", "p1"]   ← 인물 + 공간, 상한 2
   │
   └─ ⑤ 이미지 생성  ref_ids 를 실제 파일로 풀어 image_urls 에 담는다
                    kind 에 따라 프롬프트 문구가 갈린다
```

①②③이 새로 생기고, ④⑤는 이미 있는 자리를 고친다.

### 왜 컷마다 판정하지 않는가

원고는 같은 사람을 여러 이름으로 부른다 — "초등학생", "학생", "꼬마", "그 아이", "아드님".
고정 목록(사장님·손님·아이)에 `desc` 한 줄로 맞추게 하면 표현이 조금만 달라져도 못 고르거나
잘못 고른다. 낱말 목록(`aliases`)으로 때워도 목록 밖의 표현에는 같은 약점이 남는다.

**원고당 한 번 캐스팅하고 컷은 그 목록에서만 고르면 그 간극이 없어진다.** 화면 설계 패스는
`shows`를 쓸 때 이미 그 인물을 서술하고 있다("초등학생이 낡은 자전거를 끌고 들어오는
미디엄 샷") — 자기가 방금 뽑은 목록에서 고르는 것이 고정 목록에 억지로 맞추는 것보다 안정적이다.

실패의 성질도 달라진다:

| | 컷마다 판정 | 원고당 캐스팅 |
|---|---|---|
| 실패 자리 | 컷마다(4번) | 원고당 한 번 |
| 사장님이 알 수 있나 | 아니오 — 영상 보고서야 | 예 — 대본 화면에서 보인다 |
| 고치는 값 | 컷마다 다시 | 인물 하나 고치면 전 컷 반영 |

## 아바타 풀 — `lib/refs.js`

`lib/voices.js`(`VOICES`)와 같은 꼴이다. 목록은 순수 데이터라 코드가 쥐고, 파일은 자산에 둔다.

```js
export const AVATARS = [
  { id: "av-child", file: "child.jpg", kind: "person", traits: "10세 전후 아이",   label: "아이" },
  { id: "av-owner", file: "owner.jpg", kind: "person", traits: "40~60대 남성",     label: "사장님" },
  { id: "av-adult", file: "adult.jpg", kind: "person", traits: "20~40대 성인",     label: "손님" },
];
```

- 파일은 `assets/refs/`. **사장님이 직접 넣는다**(2026-07-28 결정)
- `label`은 사장님이 읽는 말, `traits`는 **캐스팅 프롬프트에 넘기는 설명**(LLM 이 이걸 보고
  인물에 맞는 아바타를 고른다), `kind`는 프롬프트 문구를 가른다
- **`traits` 매칭을 코드가 하지 않는 이유:** "10세 전후 아이"와 "초등학생"을 코드로 맞추려면
  낱말 목록이 필요하고, 그 목록은 사장님이 지적한 약점(표현이 조금 달라지면 못 고른다)을
  그대로 갖는다. 아바타 풀은 작고 설명이 붙어 있으니 캐스팅 패스가 고르는 편이 안정적이다.
  잘못 고르면 2단계 출연 블록에서 사장님이 고친다
- **파일이 없는 항목은 조용히 빠진다.** 폴더가 비어 있어도 아무것도 부러지지 않는다
- `lib/voices.js`가 분리된 이유(클라이언트가 import 하면 번들에 `fs`가 들어간다)가 여기도
  적용된다 — 목록은 `lib/refs.js`에 순수 데이터로 두고, **파일 존재 확인은 서버 쪽에서만** 한다

나중에 아바타 생성 기능이 이 풀을 채운다. 지금은 준비된 이미지로 간다 — 코드는 3장이든
30장이든 같다.

### `kind` 가 필요한 이유

지금 코드는 레퍼런스가 있으면 무조건 이렇게 붙인다:

> Match the product/subject appearance to the attached reference image exactly
> (shape, colors, packaging).

**사람에게는 틀린 지시다.** `kind: "person"`이면 "첨부된 인물과 같은 사람으로, 얼굴·머리·복장을
유지" 쪽으로 간다. 업로드 사진 중 사물은 지금 문구를 그대로 쓴다.

## 고치는 자리

| 파일 | 무엇 |
|---|---|
| `lib/refs.js` | **신규** — 아바타 목록(순수 데이터) |
| `lib/cast.js` | **신규** — 캐스팅 프롬프트 + 사진 우선 적용(순수 함수) |
| `lib/validate.js` | `validateCast` 신규, `validateShows`가 `ref_ids` 배열을 받는다 |
| `lib/cuts.js` | `buildShowsMessages`가 캐스팅 목록을 넘긴다 |
| `lib/vlm.js` | 사진 판정 함수 추가 |
| `lib/pipeline.js` | `runSplitPipeline`에 ①②③을 끼운다, `refs` 배열을 넘긴다 |
| `lib/imagegen.js` | `refImagePath` 하나 → `refs: [{path, kind}]` 배열 |

### 데이터

```js
project.cast = [
  { id: "c1", who: "가게 주인",     avatar_id: "av-owner",  // ① 이 골랐다
    ref: { from: "photo",  id: "p2" } },                    // ③ 이 사진을 우선했다
  { id: "c2", who: "초등학생 아이", avatar_id: "av-child",
    ref: { from: "avatar", id: "av-child" } },              // 붙은 사진이 없다
];
project.material.photos[n].vision = { person: false, what: "가게 내부", who: null };
cut.ref_ids = ["c2", "p1"];   // cast id 또는 photo id, 최대 2
```

> `ref.from`은 **출처**("photo" | "avatar")이고, `AVATARS[].kind`는 **프롬프트 문구를 가르는
> 종류**("person" | "thing")다. 서로 다른 것이라 이름을 갈라 뒀다 — 한 이름을 쓰면 나중에
> 반드시 헷갈린다.

`cut.ref_photo_id`(단수)는 **읽기만 유지한다** — 옛 프로젝트가 그 값을 갖고 있다.

### 우선순위와 상한

- 업로드 사진이 먼저다. 사장님이 실제로 올린 것이 아바타보다 중요하고, 2장 상한에 걸릴 때
  잘려나가면 안 된다
- 상한 2장: 인물 하나 + 사물/공간 하나. 장수가 늘면 모델이 무엇을 따를지 헷갈린다

## 사장님이 확인하는 자리 (2단계)

대본 화면 구성 목록에 **출연 블록**을 둔다. 인물마다 한 줄:

```
가게 주인 (50대 남성)       [올린 사진: 사장님.jpg ▾]
초등학생 아이 (10세 전후)    [아바타: 아이 ▾]
```

드롭다운으로 바꾼다 — 다른 아바타로, 다른 사진으로, "레퍼런스 없이". **인물 2~3명에 대해
한 번**이고, 고치면 그 원고의 모든 컷에 반영된다.

이 자리가 있어야 ①②의 오판을 **값을 치르기 전에** 잡는다. 없으면 영상을 보고서야 안다.
구성(컷·화면·움직임)을 승인 앞에서 보여주는 것과 같은 이유다.

## 실패했을 때 — 전부 "지금 동작"으로 내려앉는다

| 실패 | 결과 |
|---|---|
| `assets/refs/`가 비었다 | 아바타 배정이 안 되고 지금처럼 동작 |
| 캐스팅 패스 실패 | `cast`가 비고 컷은 사진 레퍼런스만 쓴다 |
| VLM 사진 판정 실패 | 그 사진을 사물로 취급 — 인물 자리는 아바타로 메워진다 |
| 인물이 안 나오는 원고 | `cast`가 비어 아바타를 안 쓴다 |
| 캐스팅이 고른 아바타의 파일이 없다 | 그 인물은 레퍼런스 없이 간다(지금 동작) |
| 캐스팅이 목록에 없는 아바타 id 를 뱉었다 | `validateCast`가 조용히 제거 — `validateShows`가 없는 사진 id 를 지우는 것과 같은 방어 |

**새 기능이 기존 흐름을 막지 않는 것이 이 설계의 방어선이다.** 캐스팅·판정은 실패해도
컷은 남는다 — `runSplitPipeline`의 기존 원칙(2패스가 실패해도 컷은 남는다)과 같다.

## 테스트

순수한 자리를 갈라 테스트한다(`stillOnly`에서 한 방식).

- `resolveCastRefs(cast, photos, availableIds)` — **순수 함수.** ③이다. 사진이 붙은 인물은
  사진을, 아닌 인물은 `avatar_id`를 쓴다. 파일이 없는 아바타 id 는 비워 둔다
- `resolveRefs(cut, project, availableAvatars)` — **순수 함수.** `ref_ids`를 경로·kind 로 풀고
  업로드 우선·2장 상한을 적용한다. 옛 `ref_photo_id` 폴백 포함
- `availableAvatars()` — 파일이 있는 항목만 (여기서만 `fs`를 만진다)
- `validateCast` — 스키마 방어. 실패 시 `null`(호출측이 재시도 판단) — 기존 관례
- `generateImage` — `image_urls`에 두 장이 담기는지, `kind`별 문구가 갈리는지 (주입 패턴)
- `buildShowsMessages` — 캐스팅 목록이 프롬프트에 들어가는지, 비었을 때 `(없음)`인지

기존 **338 그린이 하한선**이다.

## 단계

**1단계 — 배선과 자동 배정** (①②③④⑤ + 테스트). 파일을 넣으면 한 편 관통으로 눈으로
확인할 수 있다. 인물 일관성의 본체다.

**2단계 — 출연 블록**. 1단계에서 자동 배정이 얼마나 맞는지 보고 만든다. 오판이 드물면 표시만으로
충분할 수도, 잦으면 수정이 필수일 수도 있다 — **1단계 관측이 이 화면의 모양을 정한다.**

## 검증하지 못한 가정

여기까지 전부 문서 없이 세운 추정 위에 있다. 오늘 i2v 눈금(422)이 정확히 그런 자리였다.

1. **`nano-banana/edit`가 `image_urls` 두 장을 둘 다 반영하는지 모른다.** 첫 장만 본다면
   2장 상한이 무의미해지고 우선순위를 다시 정해야 한다
2. **아바타 한 장으로 컷 사이 인물이 실제로 같아지는지 모른다.** `nano-banana/edit`가 얼굴을
   얼마나 유지하는지가 이 기능의 값어치를 전부 정한다
3. **VLM이 사진 속 인물의 `traits`를 쓸 만하게 뽑는지 모른다.** 오늘 검수 VLM은 4컷 전부
   "오류 없음"으로 통과시키며 허공을 잡은 손을 놓쳤다 — 이 VLM 을 낙관할 근거가 약하다

세 가지 모두 **파일을 넣고 한 편 돌려야** 답이 나온다. 그때까지 "배선은 됐다"까지만 주장한다.

> 무료로 확인할 수 있는 것을 먼저 다 한다 — 테스트, `SHOTFORM_FAKE=all`, OpenAI 단독 경로.
