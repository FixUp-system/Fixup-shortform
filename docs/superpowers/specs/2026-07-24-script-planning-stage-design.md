# 대본 앙상함 보완 — 기획(분석) 단계 신설

날짜: 2026-07-24 / 브랜치: `feature/deferred-settings` 후속
관련: `lib/script.js`, `lib/briefing.js`, `lib/validate.js`, `app/api/projects/[id]/script/route.js`
선행: `2026-07-24-script-quality-design.md`(담담 문체·2단 생성)

## 배경

담담 문체 개편(초안→자기 교정 2단)으로 광고 티는 걷혔지만, 그 대가로 대본이 **앙상**해졌다. 사실은 다 들어가지만 "대본"이 아니라 **"요점 정리"처럼 나열**된다.

원인 진단(코드 실측):

- 지금 파이프라인은 `자료 → (사실 정리) → (사실을 담담한 문장으로 옮김)`이다. **"분석/기획"에 해당하는 칸이 비어 있다.** 각 사실을 왜 이 순서로, 무슨 각으로 엮을지 궁리하는 주체가 없어 곧장 문장화된다.
- 초안 프롬프트가 브레비티를 과하게 민다(`군살 없이`, `자료 적으면 짧게`, `한 문장에 한 가지 짧게`).
- 교정 패스가 문장을 한 번 더 깎는데, `editKeptContent` 가드는 **문단·coverage 개수만** 보고 **글자 수는 안 봐서** 사실 개수는 유지된 채 분량만 조용히 줄 수 있다.
- 재료 자체도 얕다: 브리핑은 "빠진 사실"만 최소로 되묻고 전개 소재(이야기·계기·반응)는 캐지 않는다.

실측 예(빵집 자료 144자):
```
(여는말) 매일 아침 6시, 해달빵집은 하루를 시작합니다.
(본문)   국산 밀가루와 무염버터로 반죽을 만들고, 팥은 직접 삶아 신선함을 더합니다.
(대표메뉴소개) 소금버터롤과 단팥크림빵은 해달빵집의 자랑입니다.
(희소성) 오후 3시면 대부분의 빵이 품절되니 서두르세요.
```
사실은 옮겼지만 "직접 삶는다 → 그래서 무엇이 다른가"의 전개가 없다.

## 목표

**전개를 책임지는 주체를 만든다.** 대본을 쓰기 전에 자료를 분석해 앵글과 문단 구조(각 문단이 어떤 사실을 어떤 인과·의미로 풀지)를 먼저 정하고, 초안은 그 설계를 담담하게 목소리로 옮긴다. 나열이 아니라 전개가 되게 하되, 새 사실을 지어내지 않는 담담 원칙은 유지한다.

목표 결과(같은 빵집 자료):
```
(여는말)   해달빵집은 매일 아침 6시에 반죽을 시작합니다.
(재료)     밀가루는 국산, 버터는 무염만 씁니다. 팥도 캔을 뜯지 않고 직접 삶습니다.
(그래서)   그래서 단맛이 공장 빵과 다릅니다.
(희소성)   대표 메뉴는 소금버터롤과 단팥크림빵. 오후 3시면 대부분 나갑니다.
```
사실 개수는 같지만 "직접 삶음 → 단맛이 다름"의 인과가 살아 있다.

## 바뀐 파이프라인

```
자료 + 사진
  → 브리핑 추출·확정 (게이트)            [기존 · 전개용 질문 보강 = 설계 C]
  → 기획/분석: 앵글 + 비트시트           ★신설 = 설계 A
  → 초안: 비트시트를 담담 나레이션으로    [재조정 = 설계 B]
  → 교정: 클리셰 제거·전개 보존           [재조정 + 분량 가드 = 설계 B]
  → 대본 확정 (게이트)                   [기존]
```

기획은 **내부 밑그림**이다 — 사장님에게 보여주지 않고 저장하지도 않는다(transient). 새 화면·게이트·라우트가 생기지 않는다. LLM 콜만 하나(기획) 늘어난다. `project.script` 저장 스키마는 그대로다.

## 설계 A — 기획(분석) 단계 신설

**위치:** `lib/script.js`에 `PLAN_SYSTEM` + `buildPlanMessages(project)` 추가. 대본 route가 초안 전에 호출.

**입력:** 확정 브리핑(topic·key_points·audience·takeaway·답한 질문) + 자료 원문 + 사진 목록.

**출력(기획 JSON — 문장이 아니라 설계도):**
```json
{
  "angle": "이 영상이 진짜 말하는 한 가지 — 가장 구체적이고 센 사실 기반",
  "beats": [
    { "role": "여는말",
      "facts": ["이 비트가 쓸 자료 사실"],
      "point": "그 사실을 어떤 인과·상황·의미로 풀지 — 왜 이게 포인트인지 (한 문장)" }
  ]
}
```

**규칙(PLAN_SYSTEM):**
- beats는 3~8개(지금 문단 범위와 동일).
- `angle`은 자료에서 가장 구체적이고 센 사실을 고른다. 광고 문구가 아니다.
- `point`의 전개는 **그 사실이 스스로 함의하는 데까지만**. 새 주장을 지어내지 않는다.
  - OK: "시럽 안 씀 → 그날 딸기에 따라 단맛이 다름"(자료가 함의).
  - 금지: "시럽 안 씀 → 건강에 좋음"(자료에 없는 새 주장).
- `facts`는 자료·브리핑에 실제로 있는 것만. 없으면 그 beat를 만들지 않는다.
- 이 단계는 문장을 쓰지 않는다 — 설계도만. 담담 톤·금지어는 여기서 신경 쓰지 않는다(초안·교정이 담당).

**검증(`lib/validate.js` `validatePlan(obj)`):**
- `angle`이 비지 않은 문자열, `beats`가 비지 않은 배열.
- 각 beat는 `role`(비지 않은 문자열)·`point`(비지 않은 문자열)·`facts`(문자열 배열, 빈 배열 허용).
- 하나라도 어긋나면 `null` 반환 → route가 재시도/폴백 판정.

## 설계 B — 초안·교정 재조정 + 분량 가드

**초안 `buildScriptMessages(project, instruction, plan)`:**
- 인자에 `plan` 추가. plan이 있으면 프롬프트에 비트시트를 실어 "각 beat를 순서대로 한 문단으로 쓰고, `beat.point`의 전개를 문장으로 살려라 — 나열하지 말고 인과·상황·의미가 드러나게. beat의 `role`을 문단 tag로 쓴다."
- 브레비티 재정의: **"군살 = 클리셰·필러다. 전개는 군살이 아니다."** 과잉 압축 문구(`군살 없이`, `자료 적으면 짧게`)를 제거/완화한다. "한 문장에 한 가지"는 명료성 규칙이라 유지한다.
- 금지어 목록·담담 톤·coverage 나열·과장 금지는 유지.
- 브리핑·자료 원문은 지금처럼 함께 주입한다(원문이 beat가 놓친 디테일을 준다).
- **안전판:** `plan`이 null이면 오늘 동작 그대로 — 브리핑+자료로 직접 초안. 기획은 강화 레이어일 뿐 하드 의존이 아니다. plan 없는 옛 흐름·기획 실패 모두 이 경로로 흡수된다.

**교정 `buildScriptEditMessages(draft)`:** 입력은 초안뿐(기존 유지). EDIT_SYSTEM 재정의:
- "클리셰·광고 티·무른 명령형은 걷되 **인과 사슬을 단문으로 뭉개지 마라. 문단의 전개와 분량을 보존한다.**"
- 기존 "사실을 하나도 빠뜨리지 않는다"에 "**줄이지 말고 사실 간 연결(인과)을 유지한다**"를 더한다.

**`editKeptContent(draft, edited)` 분량 바닥:** 기존 판정(문단 수·coverage 개수 감소 시 폴백)에 더해:
- 교정본 총 글자 수(공백 제외)가 초안의 **80% 미만**이면 `false`(초안 채택).
- 0.8은 시작값이고 라이브로 튜닝한다. 클리셰 제거만으로는 20%를 넘게 줄지 않으므로, 그 이상 줄면 전개가 뭉개진 것으로 본다.

**route(`app/api/projects/[id]/script/route.js`) 흐름:**
```
0. plan = validatePlan(callJson(buildPlanMessages))   ← 신설, 최대 2회, 실패해도 던지지 않고 plan=null
1. draft = validateScript(callJson(buildScriptMessages(project, instruction, plan)))  ← 최대 2회
2. edited = validateScript(callJson(buildScriptEditMessages(draft)))  ← 최대 2회, 실패 시 break
3. script = editKeptContent(draft, edited) ? edited : draft
4. 저장(status:"script", version++, briefing_version 각인)  ← 기존과 동일
```
기획 실패는 502가 아니다 — plan=null로 두고 초안 단계가 폴백 경로를 탄다. 대본이 아예 안 나오는 것보다 낫다.

## 설계 C — 브리핑 전개용 질문 (재료 확보)

`lib/briefing.js` SYSTEM에 **두 번째 질문 부류**를 더한다. 지금은 "빠진 사실"(자료에 없어 대본이 뭉뚱그려질 것)만 물었다. 여기에:

- **자료가 얕을 때만** 전개용 질문을 채운다. 판정은 프롬프트가 한다: "자료가 3문단 분량의 대본을 전개하기에 부족하면(사실이 적거나 이야기가 없으면)".
- 전개용 질문 후보: **왜 시작했나 / 손님·이용자 반응 / 기억에 남는 구체적 한 장면 / 남과 다른 점.** 이건 빠진 사실이 아니라 대본에 살을 줄 소재다.
- 기존 규칙과 충돌하지 않게 구분을 명시한다: "표현·취향은 묻지 않는다"는 **말투를 어떻게 꾸밀지**를 뜻하지 이야기 소재가 아니다. 전개용 질문은 소재를 캐는 것이라 허용된다.
- 우선순위: 빠진 사실 질문이 먼저다. 그걸로 슬롯이 남고 자료가 얕으면 전개용으로 채운다.
- 마찰 상한 유지: `validateBriefing`의 **질문 3개 캡은 그대로**. 자료가 풍부하면 여전히 빈 배열이 정답이다 — 얕을 때만 채운다.
- `mergeAsked`(질문 라운드 1회)·`validateBriefing`(3개·보기 4개 캡)·`briefingSignature`는 바뀌지 않는다.

## 테스트

- `validatePlan`: 정상 / angle 누락 / beats 빈 배열 / point 비문자열 / facts 비배열 → 각 케이스.
- `buildPlanMessages`: 브리핑·자료 원문·사진이 프롬프트에 실리는지.
- `buildScriptMessages`: plan 있을 때 beats가 실리는지 / plan이 null일 때 오늘 형태로 폴백되는지(기존 테스트 회귀).
- `editKeptContent`: 글자 수가 80% 미만으로 준 교정본 → `false`. 80% 이상 유지 → 기존대로 통과.
- route: 기획 실패(plan=null)에도 대본이 나오는지(폴백 경로).
- 브리핑: 얕은 자료에서도 질문이 3개를 넘지 않는지(`validateBriefing` 캡 회귀).

프롬프트 문구 자체의 품질(전개가 실제로 살아나는지, 앙상함이 해소되는지)은 단위 테스트 대상이 아니라 **라이브 검증**으로 확인한다. 실측 자료(빵집·딸기라떼·라떼아트)로 개편 전/후 대본을 비교한다.

## 영향 없는 것

- `project.script` 저장 스키마(paragraphs·coverage·version·briefing_version) 그대로.
- 화면·라우트·게이트 신설 없음. 기획은 저장 안 하는 내부 밑그림.
- 컷 분해·이미지·영상 등 대본 이후 단계 무영향.

## 열린 값

- 분량 바닥 비율(0.8) — 라이브로 튜닝.
- 전개용 질문 발동 임계("자료가 얕을 때") — 지금은 프롬프트 판정. 오작동하면 코드 신호(자료 길이·key_points 수)를 보조로 붙인다.
- 기획 콜 1회 추가(비용·지연) — 기획 JSON은 짧아 부담이 작다. 문제되면 초안에 합치는 폴백을 검토(단, 그러면 이 설계의 취지가 약해짐).
