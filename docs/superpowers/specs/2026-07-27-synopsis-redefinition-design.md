# 대본 재정의 — 구성(시놉시스)과 대본을 가른다

날짜: 2026-07-27
범위: A(개념·파이프라인 재정의). 스토리보드 화면은 B로 분리한다.
선행: `2026-07-24-pipeline-roadmap.md`, `2026-07-26-script-impact-design.md`

## 1. 문제

사장님이 말하는 "대본"은 영상이 **어떤 구성으로 어떤 흐름으로 무엇을 어떻게 보여주는지**다.
지금 코드의 `script`는 성우가 읽을 나레이션 문장 묶음일 뿐이라, 이름과 실물이 어긋나 있다.

어긋남에서 문제 셋이 파생됐다.

**① 기획이 매번 새로 짜여 방향이 흔들린다.**
`app/api/projects/[id]/script/route.js:17-25`는 수정 지시("더 짧게")를 받을 때도 기획을 새로 생성한다.
기획은 저장되지 않으므로 사장님이 고른 방향이 재생성마다 바뀔 수 있다.
SDD 백로그의 "beat시트가 수정 지시와 경합"이 이 문제다.

**② 화면 근거가 나레이션 문장 하나뿐이다.**
`lib/cuts.js`의 `buildImagePrompt`가 `Scene: ${cut.sentence}`를 쓴다.
대본 문장은 *귀로 듣는 나레이션*인 동시에 *AI가 그릴 화면의 유일한 근거*다.
둘은 요구가 다르다. 07-26 개편으로 대본이 짧고 세지자 화면 근거도 함께 얇아졌다.

**③ 사실이 이중으로 추적된다.**
기획의 `beats[].facts`와 대본의 `coverage`가 같은 일을 한다.

기획과 대본이 실제로 다른 것은 `point`를 문장으로 실현했는지 하나뿐이고,
구조(`role`→`tag`)와 사실은 그대로 복사된다. 그래서 둘이 포개져 보인다.

## 2. 재정의

세 개의 뚜렷한 물건으로 가른다. 핵심은 **1:1 종속**이다 —
대본 문단은 장면과 1:1로 묶이고, 컷은 장면에서 갈라져 나온다.
그래서 사장님이 승인한 구성이 끝까지 살아남는다.

| | 담는 것 | 저장 | 사장님이 봄 |
|---|---|---|---|
| **구성**(synopsis) | 앵글 + 장면 3~8개(대개 5~7) | 버전 있음 | 게이트 |
| **대본**(script) | 장면마다 낭독 문장 1개 | 버전 있음 | 게이트 |
| **컷**(cut) | 장면을 화면 단위로 분할 | 있음 | 최종 검수에서 |

화면 라벨은 **구성 → 대본**이다. `script`라는 코드 명칭은 나레이션을 가리키는 것으로 유지한다.

### 장면의 단위

장면은 컷이 아니라 **컷 여러 개가 나올 수 있는 덩어리**다.
5~7줄이면 영상 전체가 한 화면에 들어오고, 컷 분할은 뒤에서 기계적으로 한다.

컷 1:1(15~25줄)은 사장님에게 초반부터 세밀한 검수를 강요한다.
컷 단위 검수는 최종 검수 게이트에서 이미 하기로 되어 있다.

### 로드맵 §1 결정을 뒤집는다

기존 결정: *"대본 게이트를 사장님이 읽고 고칠 수 있는 물건으로 두려면 화면 묘사·카메라가 섞이면 안 된다."*

그 근거는 "사장님이 읽고 고칠 수 있게"였는데, 사장님이 정작 보고 싶은 것이 화면과 흐름이므로 전제가 틀렸다.
대신 **섞지 않고 나눈다** — 화면은 구성이, 문장은 대본이 갖는다. 게이트가 둘이므로 한 물건에 섞이지 않는다.

## 3. 데이터 모델

```js
// project.synopsis — 게이트 "구성"
{
  angle: "시럽 없이 그날 딸기로만 만들어서, 매일 맛이 다른 라떼",
  scenes: [{
    role:  "여는말",                          // 장면이 하는 일
    shows: "유리잔 속 딸기 과육이 우유와 층을 이루며 섞이는 순간, 클로즈업",
    says:  "오늘 이 한 잔은 어제와 맛이 다르다",  // 요지. 완성 문장이 아니다
    seconds: 3,                               // 배분 의도. 실측이 아니다
    facts: ["논산 설향", "아침 7시"],
    ref_photo_id: "p1"                        // 선택
  }],
  version: 1,
  briefing_version: 1
}

// project.script — 게이트 "대본". 이름 유지, 내용은 얇아진다
{
  paragraphs: [{ text: "오늘 이 한 잔은, 어제와 맛이 다릅니다." }],
  version: 1,
  synopsis_version: 1
}
```

- `shows`는 이미지 프롬프트의 원천이다. 문제 ②를 여기서 푼다.
- `says`는 대본이 문장으로 실현할 요지다. 기존 `beats[].point`의 자리이되, 화면(`shows`)과 갈라졌다.
- `paragraph.tag` 삭제 — 그 자리는 `scene.role`이 대신하고, 화면에서 인덱스로 짝지어 보여준다.
- `coverage` 삭제 — `scene.facts`가 대신한다. 문제 ③ 해소.

### `seconds`의 위상

구성 단계에는 아직 문장이 없으므로 실제 낭독 시간을 알 수 없다.
이 값은 **"이 장면에 몇 초를 쓸 것인가"라는 배분 의도**이지 실측이 아니다.
장면 길이 배분은 기획의 일부이므로 남긴다. P0의 TTS가 실측으로 덮어쓴다.
화면에는 "약 3초"처럼 근사임이 드러나게 표시한다.

## 4. 검증 (`lib/validate.js`)

- `validatePlan` → `validateSynopsis`로 승격.
  - `point` → `says`. `shows`(필수 문자열)·`seconds`(2~15) 추가.
  - `scenes` 3~8개. 빈 배열이면 `null`.
  - `ref_photo_id`는 `validateCuts`와 같이 사진 목록에 없으면 조용히 제거.
- `validateScript(obj, sceneCount)` — **장면 개수와 문단 개수의 일치를 강제**한다.
  안 맞으면 `null` → 호출측이 재시도. 이것이 1:1 종속을 지키는 유일한 장치다.
  - `tag` 요구 삭제, `coverage` 반환 삭제.
- `validateCuts`에 `scene_idx` 검증 추가 — 범위 밖이면 `null`.

## 5. 흐름

```
① 자료 → 브리핑 확정               [게이트: 브리핑]
② 구성 생성                        [게이트: 구성]  ← 신규
③ 대본 생성(초안→교정)              [게이트: 대본]
④ 컷 분할 (장면 → 컷, shows 상속)
⑤ TTS → 실측 길이
⑥ 레퍼런스 확보                    [게이트: 스타일 — 사진 없을 때만]
⑦ 컷별 이미지 생성 + QC
⑧ 영상화 + QC                     [게이트: 최종 검수]
⑨ 병합
```

로드맵 §3의 순서를 그대로 따르되 ②가 끼어들어 게이트가 하나 늘었다.
게이트를 번호로 부르면 로드맵과 어긋나므로 이름으로 부른다.

`lib/steps.js`의 단계가 6 → 7로 늘어난다.

```
①자료  ②구성  ③대본  ④목소리  ⑤이미지  ⑥영상  ⑦완성
```

`currentStepKey`는 브리핑 확정 → 구성 유무 → 대본 순으로 문턱을 본다.

### 라우트

| | 지금 | 바뀜 |
|---|---|---|
| `POST …/synopsis` | 없음 | 신규. 브리핑 확정 필요. 수정 지시 지원 |
| `POST …/script` | 기획→초안→교정 3단 | 구성 필수(없으면 400). 기획 생성 코드 삭제, 초안→교정 2단 |

구성에는 `confirmed` 플래그를 두지 않는다. "이 구성으로 대본 쓰기"를 누르는 것이 승인이다.
브리핑은 질문 응답이 있어 확정 플래그가 필요했지만 구성은 다음 단계 진입 자체가 승인이므로 상태를 하나 덜 만든다.

### 재생성의 의미

문제 ①을 여기서 푼다.

- 구성 화면의 "다시" → 앵글부터 새로. `synopsis.version++`
- 대본 화면의 "다시" / 수정 지시 → **구성은 그대로**, 문장만 다시. `script.version++`
  기획을 새로 짜지 않으므로 지시와 경합할 것이 없다.
- 구성이 바뀌면 대본 화면에 "구성이 바뀌었습니다" 배지.
  `app/create/[id]/script/page.js:86-87`의 `briefing_version` stale 패턴을 그대로 쓴다.

## 6. 연쇄 변경 (`lib/cuts.js`)

`shows`를 만들어놓고 쓰지 않으면 문제 ②가 그대로 남으므로 여기까지가 이 스펙의 범위다.

- `buildCutsMessages`가 대본 문장과 함께 장면의 `shows`를 주입하고,
  컷은 **장면 경계를 넘지 않는다**. 컷마다 `scene_idx`가 붙는다.
- `buildImagePrompt`의 `Scene:` 원천이 `cut.sentence` → 그 컷이 속한 장면의 `shows`로 바뀐다.
  나레이션 문장은 화면 근거에서 빠진다.

로드맵 P0의 "컷 스키마 보강(`role`·`visual_description`)"은 별도 작업이 아니라
구성에서 상속받는 것이 된다. `mood`는 이 스펙 범위 밖이다.

## 7. 화면 (최소)

- `/create/[id]/synopsis` 신규 — 앵글 + 장면 목록(역할·보여줌·할 말·약 N초)을 텍스트 형태로.
  **스토리보드 카드 디자인은 B로 미룬다.** 실제 LLM 출력을 보고 디자인해야 `shows`가 한 줄인지 세 줄인지를
  상상이 아니라 실물로 정할 수 있다.
- `/create/[id]/script` — `tag` 대신 장면 역할을 라벨로 쓰고, `coverage` 블록을 걷어내고, stale 배지를 붙인다.

## 8. 기존 데이터

마이그레이션하지 않는다. `data/*.json`은 로컬 개발 데이터뿐이고 Supabase 이행 전이다.
구성이 없는 프로젝트는 구성 단계로 되돌아간다.

## 9. 테스트

- **단위**
  - `validateSynopsis` — 필드 누락, `seconds` 범위, 장면 수 경계, 없는 `ref_photo_id` 제거
  - `validateScript` — 장면 수와 문단 수 불일치 시 `null`
  - 프롬프트 계약 — `shows`와 `says`가 갈라져 있고, `says`가 완성 문장이 되지 않게 지시하는지
  - `shows`가 `buildCutsMessages` → `buildImagePrompt`까지 도달하는지
- **회귀** — 기존 107개 중 `tag`·`coverage`·`plan`에 의존하는 것 정리
- **라이브** (`.superpowers/sdd/live-verify.mjs` 확장, 자료 4건)
  - ⓐ `shows`가 실제로 그릴 수 있는 화면인가
  - ⓑ `says`가 완성 문장 전사가 아닌가
  - ⓒ 대본이 장면 수를 지키는가
  - ⓓ 금지어 0이 유지되는가 (07-26 개편의 성과를 깨지 않았는지)
